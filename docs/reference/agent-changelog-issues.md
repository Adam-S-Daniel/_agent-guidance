# Issues filed from the agent changelogs

A loose spec for the GitHub issues opened while writing an entry in
[`agent-claude-code.CHANGELOG.md`](agent-claude-code.CHANGELOG.md) or
[`agent-codex.CHANGELOG.md`](agent-codex.CHANGELOG.md). A target repo's own
`AGENTS.md` wins where the two disagree.

## When to file

- **One issue per change group per affected repo.** A group that touches three
  repos gets three issues, each written for its own repo.
- **Name the surface or don't file.** An issue needs a file, test, doc line,
  setting or pin in the target repo that the change touches. "Might be
  relevant" with nothing named stays out of the changelog entry too.
- **Search first.** Check the target repo's open and closed issues. If one
  already covers the change, link it in the group's **Issues** line instead of
  filing a duplicate.

## Title

`<Agent> <version or range> <what changed>: <what it touches here>`

For example: `Claude Code 2.1.214 SessionStart reports fork: fleet hooks match
startup|resume`.

- Keep it under about 110 characters.
- Don't put `<placeholder>` text in a title; GitHub strips it. Write `NAME` or
  `N` instead.

## Body, in this order

1. **Lead line.** `Preliminary: found while writing <changelog path>,
   entry <date>, group <N> ("<group title>"), in <PR link>. Not yet verified
   against this repo.`
2. **`## <Agent> change(s)`.** Every quote from the group, exact and oldest
   first, each followed by its release-page link. Put Codex quotes in
   ` ```text ` fences, because their `(#NNNN)` would autolink to this repo's
   issues.
3. **`## Why it may matter here`.** One bullet per affected file, claim, test
   or pin, saying what the change does to it.
   - Write only what you read in the file.
   - Say "may" wherever you have not measured the behavior.
4. **`## To check`.** Checkboxes for:
   - the measurements to take, with the minimum agent version;
   - the docs, tests and pins to update.

   Respect the repo's one-way doors and gates (for example, skill directory
   names, `docs/skill-impact.md`, `docs/guidance-impact.md`, touch gates).
5. **`## If behavior and the changelog disagree`.** The fixed block below,
   verbatim, with `<agent>` and `<Agent>` filled in.
6. **Footer.** `---` and then `_Generated by [Claude Code](https://claude.ai/code)_`.

### Fixed block

```markdown
## If behavior and the changelog disagree

While working this issue, if <Agent> does something the quoted changes don't
describe, or doesn't do what they say:

- Record it in `_agent-guidance`'s
  [`docs/reference/agent-<agent>.DISCREPANCIES.md`](https://github.com/Adam-S-Daniel/_agent-guidance/blob/main/docs/reference/agent-<agent>.DISCREPANCIES.md),
  using the template at the top of that file, via a PR to `_agent-guidance`.
- Read the vendor docs only if the changelog is ambiguous, and quote the
  passage you relied on.
- Link the entry from this issue before closing it.
```

## Hygiene

- **Links:** link vendor release pages only. Put upstream issue references in
  code spans (`anthropics/claude-code#6235`). A link or bare reference posts a
  backlink on the vendor's public issue.
- **Mentions:** put any `@name` token in a code span, or it mentions a user.
- **Closing keywords:** never write one (`fixes #N`, `closes #N`) unless
  closing is intended.
- **Labels:** none required. The fleet has no vendor-change label.

## Closing

- **Completed:** when the checks are done. Link the PR.
- **Not planned:** when the change turned out not to matter. Give one line
  saying why.

Either way, first make sure any discrepancy found is recorded in the
`DISCREPANCIES.md` sidecar and linked from the issue.
